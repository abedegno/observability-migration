# Support and maintenance

The repository owner, [abedegno](https://github.com/abedegno), approves releases,
profile promotions and support-contract changes. Contributors and automated
agents are not assigned ongoing maintenance duties by contributing code.

Use [GitHub issues](https://github.com/abedegno/observability-migration/issues)
for installation defects, supported-profile failures and feature requests. Include
package/Python/OS versions, command/options, a redacted error and an authorised
minimal reproduction. Do not upload customer archives, credentials, signed URLs
or private object names. Source hashes alone do not require sharing original data.
Use [security reporting](SECURITY.md) for possible vulnerabilities; its fallback
applies when private vulnerability reporting is unavailable.

Maintenance is best effort, prioritising data loss, byte/time/metadata/provenance
mismatches, unsafe acceptance, source changes and unintended writes, then setup
and supported-interface defects, then performance and new profiles. No response
deadline, commercial support, monitored private inbox or long-term support branch
is promised. The latest published release is the primary maintenance target;
backports are considered individually. Old assets remain available with their
historical qualifications, not an unlimited support promise.

Changes require focused verification and review. New physical profiles require
authentic authorised fixtures, independent references and complete fidelity,
source-stability and refusal gates. Release assets are frozen before exact-artifact
qualification and owner approval. Published files and tags are never replaced.
Confirmed fidelity defects need affected-version/profile and recovery guidance;
retain originals and re-extract through a verified path rather than repairing or
dropping proprietary records silently.

The [offline access contract](docs/support-contract.md) defines the stable
release's finite interface and profile boundary. Experimental interfaces and
format flags remain explicit. Stable publication requires its own exact-asset
approval; prerelease publication does not silently promote those interfaces.
